# 5\. 非功能需求

## 5\.1\. 性能需求

**并发与容量指标**



|指标项|要求|说明|
|---|---|---|
|并发用户数|≥1000|同一时刻向系统发起请求的用户数|
|在线用户数|≥5000|同时保持登录状态的用户数|
|峰值吞吐量|≥2000 TPS|系统每秒可处理的事务请求总量|



**响应时间指标**



|指标项|要求|适用场景|
|---|---|---|
|平均响应时间|≤1秒|所有API请求的平均响应耗时|
|P95响应时间|≤3秒|95%的API请求响应耗时上限|
|P99响应时间|≤5秒|99%的API请求响应耗时上限|
|页面首屏加载|≤2秒|Web前端首屏完整渲染耗时|
|静态资源加载|≤1秒|图片、CSS、JS等静态资源请求耗时|



**资源利用指标**



|指标项|要求|说明|
|---|---|---|
|CPU使用率|≤70%|各服务实例在正常负载下的CPU占用上限|
|内存使用率|≤80%|各服务实例在正常负载下的内存占用上限|
|数据库连接池利用率|≤75%|数据库连接池中活跃连接占比上限|
|磁盘IO利用率|≤70%|数据库服务器磁盘IO使用率上限|



**稳定性指标**



|指标项|要求|说明|
|---|---|---|
|错误率|≤0\.1%|所有请求中返回4xx/5xx错误的比例|
|请求成功率|≥99\.9%|成功请求占总请求的比例|
|接口超时率|≤0\.5%|响应时间超过10秒的请求占比|



**各子系统性能分级**



系统依据业务关键程度对接口性能实行分级管理：



|优先级|业务类型|平均响应时间|P95响应时间|
|---|---|---|---|
|P0\-核心|用户登录、Token验证、权限校验|≤500ms|≤1s|
|P1\-重要|报考提交、支付确认、成绩查询|≤1s|≤2s|
|P2\-普通|信息列表查询、报表生成、数据导出|≤2s|≤5s|
|P3\-低优|批量导入、报表导出、历史日志查询|≤5s|≤10s|









## 5\.2\. 安全性需求

- **统一身份认证**：系统须提供全局统一的账户认证服务，基于JWT实现无状态认证，Token在子系统间共享，用户登录后跨子系统访问无需重新认证。

- **RBAC权限模型**：系统须实现基于角色的访问控制模型，权限不直接绑定用户，而是通过“用户→角色→权限”的间接授权链路进行管理。

- **最小权限原则**：系统默认拒绝所有未明确授权的访问请求，用户仅能执行其被分配角色所包含的操作。

- **权限粒度控制**：权限验证须达到“资源\+操作”级别，系统须在API层面拦截请求并校验用户是否具备对特定资源执行特定操作的权限。

- **部门数据隔离**：系统须结合部门模型实现数据范围控制，用户默认仅能访问其所属部门及其下级部门的数据，跨部门数据访问须经显式授权。

- **会话安全**：所有认证Token须设置合理的过期时间，支持主动登出使Token失效，防止重放攻击。

- **审计日志**：所有涉及权限变更、角色分配、登录认证的操作须记录完整的审计日志，包含操作人、时间、IP地址、操作内容及结果。

    

    

    

    

## 5\.3\. 可用性需求

**核心可用性指标**



- **系统整体可用性**：系统年度可用性须达到 **99\.9%**（即年度计划外不可用时间累计不超过8\.76小时）。

- **核心服务可用性**：账户模块（认证与鉴权）的可用性须达到 **99\.95%**，年度不可用时间不超过4\.38小时。

    

**故障隔离与容错**



- **子系统故障隔离**：单个业务子系统的宕机或故障不得影响其他子系统的正常运行。API网关须具备熔断机制，当某子系统连续失败超过阈值时自动熔断，15秒后进入半开状态尝试恢复。

- **数据库故障切换**：数据库主节点故障时，须在60秒内自动切换至备用节点，切换过程对上层服务透明。

- **通用模块降级**：当通知、消息、邮件等非核心通用模块不可用时，各业务子系统的核心业务流程不得被阻塞，须具备优雅降级能力。例如：邮件服务不可用时，系统须将待发送邮件写入持久化队列，待服务恢复后自动补发。

    

**服务恢复指标**



|恢复项|目标时间|说明|
|---|---|---|
|单服务实例故障摘除|≤30秒|健康检查探测到故障后，自动从负载均衡中摘除|
|新实例启动接入|≤60秒|新实例启动完成并开始接收流量|
|数据库故障恢复|≤30分钟|基于WAL/binlog增量备份的数据库恢复至可用状态|
|异地灾备切换|≤2小时|主站点灾难性故障后，完成异地切换并恢复服务|
|单服务实例重启|≤30秒|服务实例从停止到可接受请求的完整重启耗时|



**健康检查机制**



- 所有服务实例须暴露`/health`端点，供API网关或负载均衡器定期探测。

- 健康检查探测间隔不超过15秒，连续3次探测失败判定服务不可用。

- 数据库及Redis连接状态须纳入健康检查范围，依赖服务不可用时健康检查也应返回不健康状态。

    

**维护窗口管理**



- 计划内维护须提前48小时通知相关方，并在业务低峰期执行。

- 单个子系统的计划维护不得影响其他子系统的正常服务。

- 维护窗口内产生的不可用时间不计入可用性指标。

    

**数据灾备**



- 数据库备份文件须每日全量备份一次，每分钟增量备份一次。

- 备份文件须异步同步至异地数据中心，异地备份保留周期不少于30天。

- 文件及对象存储须启用跨区域复制或定时同步机制，保障文件数据不因单一存储节点损坏而丢失。

    

    

    

    

## 5\.4\. 可维护性需求

**代码管理**



- 前端与后端代码仓库须完全分离，各自独立维护。

- 各子系统后端代码、各通用模块代码须分属独立仓库，互不干扰。

- 每个仓库须包含清晰的README文档，说明项目结构、本地运行方式、依赖项及构建部署流程。

    

**API契约维护**



- 所有API须基于OpenAPI 3\.1规范维护契约文件，契约文件为前后端协作的唯一依据。

- API契约变更须遵循“先更新契约，评审通过后再同步开发”的流程。

- 契约文件须纳入版本控制，与代码变更同步提交。

    

**编码规范**



- 前端代码须遵循统一的TypeScript/Vue3编码规范，使用ESLint \+ Prettier进行代码格式化。

- 后端代码须遵循其官方编码规范。

- 各仓库须配置CI流水线，在代码提交时自动执行代码检查与单元测试。

    

**日志与监控**



- 所有服务须输出结构化日志（JSON格式），包含时间戳、服务名、请求ID、日志级别、消息内容。

- 日志级别须可动态调整，支持DEBUG、INFO、WARN、ERROR四级。

- 关键业务操作（认证、授权、数据变更）须记录审计日志，包含操作人、时间、IP、操作内容及结果。

    

**文档要求**



- 每个子系统须维护独立的详细设计文档及接口文档。

- 部署运维文档须涵盖环境要求、部署步骤、配置参数说明、常见故障处理方案。

## 5\.6\. 可扩展性需求

**水平扩展能力**



- 各业务子系统及通用模块须设计为无状态服务，支持通过增加实例数量的方式进行水平扩展。

- API网关须支持对后端服务实例的负载均衡，新增实例自动接入流量分发。

- 数据库须支持读写分离架构，当读压力增长时可通过增加只读副本扩展读能力。

    

**功能扩展能力**



- 新增业务场景时，须以独立子系统形式开发部署，不影响现有系统的运行。

- 通用模块提供的API须保持稳定，新增功能以新增接口或接口版本升级的方式提供，不得破坏现有接口的兼容性。

    

**移动端扩展预留**



- 所有业务API须与前端UI层充分解耦，API设计不依赖特定的客户端实现。

- 当前Web客户端实现的所有业务功能，后续均可通过复用已有API开发iOS/Android原生应用，后端服务无需任何修改。

- API响应数据结构须避免使用Web特有的渲染逻辑字段，保持数据纯粹性。

    

**模块解耦扩展**



- 子系统间仅通过API通信，当某个子系统需要进行重大升级或技术栈迁移时，只要保持API契约兼容，即可独立完成。

- 存储适配器层的抽象设计使得底层存储方案可替换，业务模块无感知。未来如需切换对象存储服务商或协议，仅需修改适配器实现，无需改动业务代码。

- RBAC权限模型支持新增角色与自定义权限组合，不限制角色数量与权限粒度，适配组织架构的持续演化。
